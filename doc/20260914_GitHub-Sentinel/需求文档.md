# GitHub Sentinel

## 背景

开发者和项目管理人员通常需要同时关注多个 GitHub 仓库。依赖人工逐个检查容易遗漏重要 Release、Pull Request、Issue 和 Commit，也会产生重复的信息筛选工作。

## 目标

GitHub Sentinel 定期获取订阅仓库的最新动态，将不同类型的变更标准化、去重和汇总，并通过配置的通知渠道发送周期报告，帮助团队及时掌握项目进展。

## 范围

### 包含

- 创建、查询、修改和删除仓库订阅。
- 支持每日和每周两种订阅周期。
- 支持 Release、Pull Request、Issue 和 Commit 事件类型。
- 增量获取事件并避免重复入库、重复报告。
- 使用 AI 或规则引擎生成摘要。
- 生成 Markdown 报告。
- 支持 Webhook 和邮件通知的扩展接口。
- 支持手动同步、手动生成报告、健康检查。

### 不包含

- 首期不提供 Web 管理前端。
- 首期不处理实时 GitHub Webhook。
- 首期不提供企业级多租户、RBAC 或计费。
- 首期不提供知识库问答或向量检索。

## 用户场景

1. 开发者订阅依赖项目，每日接收 Release 和重要变更摘要。
2. 项目经理订阅团队仓库，每周查看 Pull Request、Issue 和 Commit 汇总。
3. 运维人员通过 API 手动触发同步，检查采集和报告链路是否正常。
4. 用户在 AI 服务不可用时仍能收到基于规则生成的报告。

## 功能与业务规则

- 仓库使用唯一的 `owner/name` 标识。
- 一个订阅至少选择一种事件类型，并使用有效的 IANA 时区。
- 数据保存成功后才能推进同步游标。
- 相同订阅、事件类型和 GitHub 外部事件 ID 的事件不得重复保存。
- 同一订阅和同一报告周期只能产生一份逻辑报告。
- 报告生成和通知发送相互独立；通知失败不得丢失已生成报告。
- 未配置 AI 或 AI 调用失败时，应降级为规则摘要。
- 单个通知渠道失败不得阻止其他渠道投递。
- 未启用的订阅不执行采集、报告或通知。

## 边界情况

- GitHub 无新事件时，自动同步不生成报告。
- GitHub 限流或暂时不可用时，后续实现应延迟重试并保留同步游标。
- 应用重试同一时间窗口时，事件去重与报告幂等规则仍然生效。
- 删除不存在的订阅、查询不存在的报告均返回资源不存在错误。
- 阶段一使用内存仓储，进程重启后数据清空；该限制将在持久化阶段移除。

## 验收标准

- 应用能够启动并公开 OpenAPI 文档。
- 存活与就绪检查返回成功状态。
- 订阅 CRUD API 可用，且能够校验仓库格式、事件类型和时区。
- 使用假 GitHub 客户端时，一次同步可完成事件保存和报告生成。
- 重复同步相同事件不会生成重复事件或报告。
- 未配置 AI 时能够生成规则摘要。
- 管理接口在配置 API Key 后拒绝未授权请求。
- 单元测试和核心集成测试通过。

## 影响范围

- 新增 GitHub Sentinel Python 项目。
- 新增 HTTP API、领域模型、应用服务及适配器边界。
- 新增本地与容器运行配置。
- 后续阶段将引入 GitHub Token、数据库、Redis、AI 和通知渠道凭据。

## 待确认事项

- 第二阶段是否优先支持 GitHub Personal Access Token，还是直接采用 GitHub App。
- 每周报告默认发送日和发送时间。
- “重要更新”的筛选规则及默认标签。
- 首个真实通知渠道优先实现邮件、Slack、飞书或通用 Webhook。
